Datenhaltung

Autor:in

Joern Ploennigs · AI4SC

We don’t have better algorithms. We just have more data.

— Peter Norvig

Ingenieurdaten kommen selten in einer selbst gewählten Idealform an. Meist bestimmt das Werkzeug, das die Daten erzeugt hat, auch das Format: Sensorik liefert CSV, GIS-Werkzeuge oft GeoJSON, Bürosoftware XLSX, CAD und BIM ihre eigenen Austauschformate. Deshalb ist Dateiarbeit keine Nebensache, sondern ein zentraler Teil des Datenmodells.

Dateien als Eingangskanal

Dateien sind Ankunftspunkte für Fachdaten

  • Dateien sind nicht nur “Speicher”
  • Dateien sind die Form, in der Werkzeuge Daten an uns übergeben
  • Das Format wird oft vom Ursprungswerkzeug bestimmt
  • Unsere Aufgabe: lesen, verstehen, prüfen, weiterverarbeiten

Engineering-Szenario 1: Messdaten aus dem Feld

Monitoring-Station

  • Zeitreihen als CSV
  • Oft ; statt ,
  • Fehlwerte als -9999 oder leer
  • Umlaute in Kopfzeilen sind möglich

Fragen vor dem Einlesen

  • Welche Kodierung?
  • Welches Trennzeichen?
  • Hat die Datei eine Kopfzeile?
  • Wie sind fehlende Werte markiert?

Engineering-Szenario 2: Modelle aus anderen Werkzeugen

GIS / Umweltinformatik

  • Geometrien oft als GeoJSON
  • Struktur ist verschachtelt
  • Attribute liegen in properties

BIM / Planung

  • Modelle als IFC, XML oder JSON-Varianten
  • Große Dateien, viele Objekte
  • Fachlogik steckt im Format

Die erste fachliche Frage lautet daher selten “Wie programmiere ich Lesen?”, sondern “Was hat das Werkzeug, das die Datei erzeugt hat, eigentlich gemeint?”. Gerade mit KI-generiertem Code ist diese Unterscheidung wichtig, weil das Modell oft ein plausibles, aber falsches Standardformat annimmt.

Speicher und Dateisysteme

Wo liegen unsere Daten?

Smartphones und Tablets

  • App-bezogene Datenhaltung
  • Starke Kapselung
  • Wenig direkte Dateisicht

Desktop-PCs

  • Dateien in Ordnerstrukturen
  • Direkte Arbeit mit Pfaden
  • Typisch für Python-Skripte

Web- und Cloudsysteme

  • Daten verteilt auf Servern
  • Häufig Datenbanken im Hintergrund
  • Dateien oft nur Import/Export-Schnittstelle

Speicherhierarchie im Computer

  • Register und Cache: sehr schnell, sehr klein
  • RAM: schnell, aber flüchtig
  • SSD/HDD: langsam im Vergleich, aber dauerhaft
  • Dateien liegen im permanenten Speicher

Von RAM zu Datei

Während das Programm läuft

  • Variablen im RAM
  • Daten können verändert werden
  • Inhalt geht beim Ausschalten verloren

Wenn Daten bleiben sollen

  • Schreiben in Dateien
  • Organisation über Dateisystem
  • Identifikation über Pfad und Dateiname

Dateisysteme organisieren Dateien

Desktop

  • Hierarchische Ordnerstruktur
  • Gut für viele unterschiedliche Dateien
  • Schnell unübersichtlich

App- und Cloud-Kontexte

  • Stärker gekapselt
  • Mehr Sicherheit
  • Weniger direkte Kontrolle

Python und Dateisysteme

  • open() für direktes Lesen und Schreiben
  • os und pathlib für Pfade, Listen, Existenztests
  • Textdateien oft zeilenweise lesen
  • Binärdateien als Bytes behandeln

Dateien mit Python

Dateien lesen und schreiben

Lesen

  • open(path, "rt")
  • mit with automatisch schließen
  • read(), readlines(), Iteration über Zeilen

Schreiben

  • open(path, "wt")
  • write() überschreibt im Modus w
  • für Binärdateien: rb und wb

KI-generierter Code: Was macht dieser Block?

with open("messung.csv", "rt") as fi:
    text = fi.read()
  • Welchen Datentyp hat text?
  • Für welche Dateitypen ist das passend?
  • Was würde bei einer Binärdatei schiefgehen?

Auflösung

  • text ist ein str
  • Passend ist das für Textdateien wie csv, json, xml oder txt
  • Bei Binärdateien würden Bytes als Text fehlinterpretiert oder schon beim Dekodieren Fehler entstehen

Dateien prüfen, auflisten, löschen

from pathlib import Path

pfad = Path("daten")

for datei in pfad.iterdir():
    if datei.is_file():
        print(datei.name)

print(Path("messung.csv").exists())
Path("temp.txt").unlink(missing_ok=True)

Formate: Text oder Binär?

Text

  • Als Zeichen lesbar
  • Gut debugbar
  • Beispiele: txt, json, xml, csv

Binär

  • Als Bytes gespeichert
  • Kompakter oder softwaregebunden
  • Beispiele: xlsx, zip, Bilder, Videos

Im Unterricht reicht oft eine grobe Zweiteilung in Text- und Binärdateien. Fachlich entscheidend ist aber die dritte Frage: Welche Struktur erwartet das erzeugende Werkzeug? Zwei Textdateien können sich völlig unterschiedlich lesen lassen, wenn eine flache CSV-Tabelle und die andere eine tief verschachtelte GeoJSON-Datei ist.

Fachformate verstehen

Typische Formate für Ingenieurdaten

Geometrie

  • DWG, DXF, IFC
  • GeoTIFF, Shapefile
  • GeoJSON

Attribute

  • CSV
  • XLSX
  • JSON

Struktur / Austausch

  • XML
  • JSON
  • ZIP als Container

JSON: strukturierte Objekte

  • Menschen- und maschinenlesbar
  • Nahe an Python-dict und list
  • Gut für APIs und Konfigurationsdaten
  • Auch Basis für GeoJSON
{
  "name": "Station 7",
  "active": true,
  "values": [12.4, 13.1],
  "location": {"x": 12.10, "y": 54.08}
}

GeoJSON: Geometrie plus Attribute

  • Standard für geographische Objekte
  • Geometrien wie Point, LineString, Polygon
  • Attribute typischerweise in properties
  • Verschachtelung ist normal, nicht die Ausnahme
{
  "type": "Feature",
  "geometry": {"type": "Point",
               "coordinates": [12.09, 54.07]},
  "properties": {"name": "OKI"}
}

XML: Markup mit Tags

  • Älter als JSON, aber weiter verbreitet
  • Gut für formalisierte Austauschstandards
  • Struktur über öffnende und schließende Tags
  • Häufig in Office- und Fachstandards
<station>
  <name>Station 7</name>
  <active>true</active>
  <value unit="m">12.4</value>
</station>

CSV: Tabellen und Messwerte

  • Sehr einfaches Tabellenformat
  • Eine Zeile pro Datensatz
  • Trennzeichen nicht immer Komma
  • Deutsche Daten nutzen oft ;
Zeit;Pegel;Status
08:00;2.41;ok
09:00;;wartung
10:00;2.55;ok

XLSX und ZIP: Container statt Klartext

XLSX

  • Excel-Arbeitsmappe
  • Für Menschen komfortabel
  • Intern mehrere XML-Dateien

ZIP

  • Verpackt viele Dateien in einer
  • Kann Inhalte komprimieren
  • Auch Fachformate nutzen ZIP als Hülle

Für Python bedeutet das: Nicht jedes scheinbar “einfache” Dateiformat ist im Inneren einfach. Eine .xlsx-Datei wirkt wie eine einzelne Tabelle, ist aber technisch ein Container aus mehreren Dateien. Deshalb sollte das Lesewerkzeug zum Format passen, nicht nur zur Dateiendung.

Ein Skript, drei Formate

import json
import pandas as pd
import xml.etree.ElementTree as ET

messung = pd.read_csv("messung.csv", sep=";", encoding="latin-1")

with open("stationen.geojson", "rt", encoding="utf-8") as fi:
    geo = json.load(fi)

xml_baum = ET.parse("station.xml")
xml_wurzel = xml_baum.getroot()

print(messung.head(2))
print(geo["features"][0]["properties"]["name"])
print(xml_wurzel.findtext("name"))
  • CSV lesen wir tabellarisch mit pandas
  • GeoJSON lesen wir als verschachteltes JSON-Objekt
  • XML lesen wir über Tags und Elemente

KI-Verifikation beim Datei-I/O

Wenn KI Dateicode erzeugt: typische Fehlannahmen

Das Modell nimmt oft an

  • UTF-8-Kodierung
  • Komma als Trennzeichen
  • Erste Zeile ist Header
  • Fehlwerte sind leer

Engineering-Daten sind oft anders

  • latin-1 oder Windows-Kodierung
  • ; oder Tabulator
  • Metazeilen vor dem Header
  • -9999, NA, ---

Verifikation mit pandas

import pandas as pd

probe = pd.read_csv(
    "messung.csv",
    sep=";",
    encoding="latin-1",
    na_values=["-9999", "NA", ""]
)

print(probe.head())
print(probe.dtypes)
  • Erst kleine Probe lesen
  • Kopfzeile und Datentypen prüfen
  • Fehlwerte sichtbar machen

KI-Code-Reading: Wo kann dieser Vorschlag scheitern?

df = pd.read_csv("messung.csv")
  1. Stimmt das Trennzeichen?
  2. Stimmt die Kodierung?
  3. Ist Zeile 1 wirklich der Header?
  4. Werden Fehlwerte korrekt erkannt?

Agentic Workflow für Datei-I/O

Agentic workflow: Wenn KI Code zum Einlesen von Dateien erzeugt: 1. Prüfe zuerst Kodierung und Trennzeichen. 2. Kontrolliere Header-Behandlung und fehlende Werte. 3. Teste auf einer kleinen echten Stichprobe vor dem Gesamtdatensatz. 4. Präzisiere den Prompt mit Formatwissen aus dem Ursprungstool.

Grenzen von Dateien

Dateien sind praktisch, aber begrenzt

Stärken

  • Einfach austauschbar
  • Direkt sichtbar
  • Gut für Import/Export

Grenzen

  • Gleichzeitiger Zugriff schwierig
  • Versionierung und Konsistenz mühsam
  • Suchen, Filtern, Verknüpfen schnell aufwendig
  • Deshalb reichen Dateien für gemeinsame, wachsende Datenbestände oft nicht mehr aus

Ausblick

  • In 11b_UIDesign lesen Dashboards Daten aus Dateien oder APIs ein
  • In 12b_Datenbanktypen sehen wir, warum Dateien allein oft nicht reichen
  • Später folgen relationale Datenbanken als robustere Mehrnutzer-Lösung

Lesson Learned

  • Dateien sind der übliche Eingangskanal für technische Daten
  • Formatwahl ist eine Modellierungsentscheidung
  • Textformat heißt nicht automatisch “einfach”
  • KI-generierter Dateicode muss immer an echten Beispieldaten verifiziert werden
